Alert responsibility settings manage who is responsible for alerts, from the settings area. They are the same records the Alert responsibilities area serves. Only the listing has been confirmed; a create, update or delete returns `403` without the `MANAGE_ALERT_RESPONSIBILITY` permission. This area has 5 endpoints, and all seven SDKs call every one.

<Warning>
  **Only the listing in this area has been confirmed.** The single read and the writes have not been confirmed on these paths; the Alert responsibilities area serves the same records.
</Warning>

## Before you call

Register your API credentials once when your app starts, as shown in
[Authentication](/authentication). Every SDK sample on these pages then gets its client in one line.
With cURL, send the access token in an `Authorization` header: `Authorization: Bearer $ACCESS_TOKEN`.

## Things to know

- **These are the same records as the Alert responsibilities area.** `/settings/alert_responsibilities` and `/alert_responsibility` serve the same alert responsibilities.
- **Writes need the `MANAGE_ALERT_RESPONSIBILITY` permission.** Without it, a create, update or delete returns `403`.
- **Alert responsibility ids start with `ar_`.** One record comes back under `alert_responsibility`, and `name` is required to create one.
- **Listings page by cursor.** Records sit under `data`; pass `pagination.next_cursor` as `cursor` to read the next page, and stop when `pagination.has_more` is `false`.
