The Exsited API uses OAuth 2.0 with the Client Credentials flow to authenticate requests. Every API call must include a valid Bearer token in the `Authorization` header. This page walks you through obtaining your credentials, requesting an access token, and making authenticated requests safely.

## Get Your API Credentials

Before you can request a token, you need three credentials from Exsited:

- **`client_id`** — A unique identifier for your integration.
- **`client_secret`** — A secret key paired with your client ID.
- **`redirect_uri`** — A URI registered to your integration.

<Info>
  Contact your Exsited account manager to receive your `client_id`, `client_secret`, `redirect_uri`, and your account-specific base URL. Keep these credentials secure and never share them publicly.
</Info>

## Request an Access Token

<Steps>
  <Step title="Prepare your credentials">
    Gather your `client_id`, `client_secret`, and `redirect_uri`. You will send these in a JSON body to the token endpoint.
  </Step>
  <Step title="POST to the token endpoint">
    Send a `POST` request to `/api/v1/oauth2/token` on your base URL. Set the `Content-Type` header to `application/json`.

    ```bash
    curl -X POST https://example.exsited.com/api/v1/oauth2/token \
      -H "Content-Type: application/json" \
      -d '{
        "grant_type": "client_credentials",
        "client_id": "your_client_id",
        "client_secret": "your_client_secret",
        "redirect_uri": "your_redirect_uri"
      }'
    ```
  </Step>
  <Step title="Store the access token">
    A successful response returns a JSON object containing your `access_token`. Store this token securely in your application for use in subsequent requests.
  </Step>
</Steps>

## Token Response

A successful token request returns a response like the following:

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600
}
```

| Field | Type | Description |
|-------|------|-------------|
| `access_token` | string | The Bearer token to include in all API requests. |
| `token_type` | string | Always `Bearer`. |
| `expires_in` | integer | Seconds until the token expires. Typically `3600` (one hour). |

## Use the Token

Include the `access_token` value in the `Authorization` header of every API request:

```bash
curl https://example.exsited.com/api/v3/accounts \
  -H "Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9..."
```

<Tip>
  Store the token and its expiry time together. Before each request, check whether the token has expired and fetch a new one proactively rather than waiting for a `401` response.
</Tip>

## Token Expiry and Refresh

The Client Credentials flow does not issue refresh tokens. When your access token expires, request a new one by repeating the same `POST /api/v1/oauth2/token` call with your credentials.

<Note>
  If the API returns a `401 Unauthorized` response, your token has expired or become invalid. Re-authenticate immediately by requesting a fresh token and retrying the original request.
</Note>

## Security Best Practices

Follow these practices to keep your integration secure:

- **Never expose credentials client-side.** Your `client_id` and `client_secret` must only exist in server-side or backend code. Never embed them in a browser, mobile app, or public repository.
- **Use environment variables.** Store credentials as environment variables rather than hardcoding them in source files.
- **Rotate secrets regularly.** Contact your Exsited account manager to rotate your `client_secret` if you suspect it has been compromised.
- **Use HTTPS exclusively.** All Exsited API endpoints are served over HTTPS. Never send credentials over plain HTTP.
- **Limit secret access.** Restrict which team members and services have access to your API credentials using your organization's secrets management tooling.

<Warning>
  If your `client_secret` is ever exposed in a public repository or log file, contact your Exsited account manager immediately to have it rotated.
</Warning>
