The Exsited REST API gives you programmatic access to the core resources that power your operations platform. Whether you are syncing customer records from a CRM, pushing orders from an e-commerce storefront, or pulling invoice data into an accounting system, the API provides a consistent, resource-oriented interface you can integrate with using any language or HTTP client.

## Base URL

Every request is made against a subdomain that is unique to your Exsited account. Replace `example` with your own subdomain in every request:

```text
https://example.exsited.com
```

<Info>
  Your base URL is provided by your Exsited account manager when your account is provisioned. All API resources are served under the `/api/v3/` path prefix.
</Info>

## Endpoint Structure

The API follows standard REST conventions. Each resource supports a predictable set of operations:

| Operation | Method | URL Pattern |
|-----------|--------|-------------|
| List | `GET` | `/api/v3/{resource}` |
| Retrieve | `GET` | `/api/v3/{resource}/{id}` |
| Create | `POST` | `/api/v3/{resource}` |
| Update (full) | `PUT` | `/api/v3/{resource}/{id}` |
| Update (partial) | `PATCH` | `/api/v3/{resource}/{id}` |
| Delete | `DELETE` | `/api/v3/{resource}/{id}` |

Not every resource exposes all six operations. Each resource reference page lists the exact methods available.

## Pagination

List endpoints return paginated results. Control the page size and position using query parameters:

| Parameter | Type | Description |
|-----------|------|-------------|
| `limit` | integer | Number of records to return. Default is `20`. |
| `offset` | integer | Number of records to skip before returning results. Default is `0`. |
| `order_by` | string | Field to sort by. Common values include `created_on`. |
| `direction` | string | Sort direction: `asc` or `desc`. Default is `desc`. |

**Example paginated request:**

```bash
curl https://example.exsited.com/api/v3/accounts?limit=20&offset=0&order_by=created_on&direction=desc \
  -H "Authorization: Bearer <token>"
```

## Error Responses

When a request fails, the API returns a JSON body describing what went wrong. Always check the `message` field for a human-readable explanation.

```json
{
  "error": "validation_error",
  "message": "The 'email' field is required.",
  "status": 400
}
```

<Tip>
  Log the full error response body during development. The `message` field often contains enough detail to resolve the issue without needing to contact support.
</Tip>

## HTTP Status Codes

| Code | Meaning |
|------|---------|
| `200 OK` | The request succeeded and the response body contains the result. |
| `201 Created` | A new resource was successfully created. |
| `400 Bad Request` | The request body or query parameters are invalid. |
| `401 Unauthorized` | The access token is missing, expired, or invalid. |
| `403 Forbidden` | Your credentials do not have permission to perform this action. |
| `404 Not Found` | The requested resource does not exist. |
| `500 Internal Server Error` | An unexpected error occurred on the Exsited server. |

<Warning>
  A `401` response means your access token has expired or is invalid. Request a new token using the OAuth 2.0 token endpoint and retry the original request. See [Authentication](/api/authentication) for details.
</Warning>
