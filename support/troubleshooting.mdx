Most issues in Exsited fall into a small set of recognisable patterns — expired credentials, misconfigured permissions, or a setting that does not quite match between connected platforms. This guide walks you through the most common problems and the steps to resolve them. Work through each section methodically and you will resolve the majority of issues without needing to contact support.

---

## Integration Authentication Expired

Your integration connection to a third-party platform (such as Xero, MYOB, or Shopify) uses an OAuth token that periodically expires. When this happens, syncs stop working and Admin users receive a notification.

**Symptoms:** Sync jobs are failing, the integration status shows **Disconnected** or **Auth Error**, and recent records are not appearing in your connected platform.

<Steps>
  <Step title="Open Integrations">
    Navigate to **Integrations** in the main menu and locate the affected platform.
  </Step>
  <Step title="Check the connection status">
    If the status shows **Disconnected** or **Authentication Required**, the token has expired.
  </Step>
  <Step title="Re-authorise the connection">
    Click **Reconnect** (or **Re-authorise**). You will be redirected to the third-party platform's login page. Sign in with the account that was originally used to connect the integration.
  </Step>
  <Step title="Confirm the connection">
    Once authorised, you are redirected back to Exsited. The integration status should change to **Connected**.
  </Step>
  <Step title="Trigger a manual sync">
    Click **Sync Now** to immediately re-process any records that failed while the connection was down.
  </Step>
</Steps>

<Note>
  OAuth tokens typically expire after 60–90 days depending on the platform. Some platforms (such as Xero) refresh tokens automatically as long as a sync runs at least once every 60 days. To avoid expiry, ensure at least one sync-triggering action occurs regularly.
</Note>

## Sync Conflicts and Duplicate Records

Sync conflicts occur when the same record is modified in both Exsited and a connected platform between sync cycles, resulting in a mismatch. Duplicate records can appear if a record is created manually in one platform after it has already been synced.

**Symptoms:** Duplicate contacts, orders, or products in Exsited or your accounting platform; records showing stale data after editing.

<Steps>
  <Step title="Review the conflict log">
    Go to **Integrations → [Platform Name] → Sync History**. Filter by **Status: Conflict** to see all unresolved conflicts.
  </Step>
  <Step title="Open each conflict">
    Click a conflict entry to see a side-by-side comparison of the Exsited version and the connected platform's version.
  </Step>
  <Step title="Choose a resolution">
    Select **Keep Exsited Version**, **Keep [Platform] Version**, or **Merge Manually** depending on which data is correct.
  </Step>
  <Step title="Resolve duplicates">
    For duplicate records, open the duplicate in Exsited and use the **Merge** action (available on Contact and Product records) to combine it with the original. This preserves transaction history.
  </Step>
  <Step title="Re-run the sync">
    After resolving all conflicts, click **Sync Now** to confirm the resolution is applied to both platforms.
  </Step>
</Steps>

<Warning>
  When you choose **Keep [Platform] Version**, the Exsited record is overwritten with the external platform's data. This action cannot be undone. Make sure you have confirmed which version is correct before proceeding.
</Warning>

## Orders Not Syncing to Accounting

If orders created in Exsited are not appearing in your accounting platform, work through this checklist before contacting support.

<Steps>
  <Step title="Check the integration status">
    Go to **Integrations** and confirm the accounting platform shows **Connected**. If not, follow the re-authorisation steps above.
  </Step>
  <Step title="Confirm the order is in the correct status">
    Most integrations only sync orders that have reached a certain status (e.g., **Confirmed** or **Invoiced**). Orders in **Draft** status are typically not synced. Check the order's status and advance it if appropriate.
  </Step>
  <Step title="Verify tax code mapping">
    Go to **Integrations → [Platform Name] → Tax Code Mapping** and confirm that every tax code used in Exsited is mapped to a corresponding code in your accounting platform. Unmapped codes will cause individual records to fail.
  </Step>
  <Step title="Check the sync log for errors">
    Navigate to **Integrations → [Platform Name] → Sync History** and look for the specific order. If it shows an error, the error message will describe the cause (e.g., missing customer, unmapped account code).
  </Step>
  <Step title="Manually push the record">
    Open the order in Exsited and click **Push to [Platform Name]** to attempt a manual sync. Check the result message for any specific error.
  </Step>
</Steps>

<Note>
  Account code mapping (linking Exsited product categories to accounting chart-of-accounts codes) is required for invoice syncing in most accounting integrations. Review your account code mappings under **Integrations → [Platform Name] → Account Mapping**.
</Note>

## User Cannot Access a Module

If a user reports that they cannot see a module or are receiving a permission error when trying to perform an action, follow these steps.

<Steps>
  <Step title="Check the user's role">
    Go to **Configuration → Users** and open the user's profile. Note their assigned role (Admin, Manager, Staff, or Viewer).
  </Step>
  <Step title="Review module-level permissions">
    Under **Module Access**, confirm that the relevant module is enabled for this user and that the permission level (None, View, Create, Edit, Delete, Approve) is sufficient for the action they are trying to perform.
  </Step>
  <Step title="Update permissions if needed">
    Adjust the module permission level as appropriate and click **Save Changes**. Changes take effect immediately on the user's next page load.
  </Step>
  <Step title="Ask the user to refresh">
    Have the user refresh their browser or log out and log back in to ensure the updated permissions are applied to their session.
  </Step>
</Steps>

<Note>
  Viewer-role users can never create, edit, or approve records regardless of module-level settings. If a user needs to perform actions, they must be assigned at least the Staff role.
</Note>

## PDF Not Generating from Portal Submission

If a PDF is not being produced after a portal form is submitted, the issue is usually in the form's submission action configuration or a missing template.

<Steps>
  <Step title="Check the submission action">
    Go to **Configuration → Custom Forms** and open the relevant form. Navigate to the **Submission Actions** tab and confirm that **Generate PDF** is enabled.
  </Step>
  <Step title="Verify the PDF template">
    Confirm that a PDF template has been selected in the **Generate PDF** action settings. If the field shows **No template selected**, choose a template or create one under **Configuration → Document Templates**.
  </Step>
  <Step title="Check required field completion">
    PDF generation can fail silently if a required field that the template references was left empty at submission. Review the template for any field references that may not have a value.
  </Step>
  <Step title="Test with a new submission">
    Submit the form yourself using the portal preview and check whether the PDF is generated. Check **Configuration → System Settings → Audit Logs** for any submission errors.
  </Step>
</Steps>

<Warning>
  If you make changes to a form that is currently assigned to a live portal, those changes apply to all future submissions immediately. Notify portal users of any significant form changes before saving.
</Warning>

## API Returning 401 Unauthorized

A `401 Unauthorized` response means your API request did not include a valid bearer token, or the token you are using has expired.

<Steps>
  <Step title="Check that you are sending the token">
    Confirm your request includes an `Authorization: Bearer <token>` header. A missing or malformed header is the most common cause of 401 errors.
  </Step>
  <Step title="Check whether the token has expired">
    API tokens generated in Exsited have a configurable expiry. Go to **Configuration → API Keys** and check the expiry date of the token you are using.
  </Step>
  <Step title="Generate a new token">
    If the token has expired, click **Generate New Key** next to the relevant API key entry. Copy the new token immediately — it is only shown once.
  </Step>
  <Step title="Update your integration or script">
    Replace the old token in your application, environment variables, or integration configuration with the newly generated token.
  </Step>
  <Step title="Re-test your request">
    Retry the API request to confirm the 401 error is resolved.
  </Step>
</Steps>

<Note>
  Exsited API tokens do not auto-refresh. If your integration runs unattended, set a calendar reminder to rotate tokens before they expire, or contact [support@exsited.com](mailto:support@exsited.com) to ask about long-lived token options.
</Note>

## API Returning 403 Forbidden

A `403 Forbidden` response means your request was authenticated correctly, but the API key or the user it belongs to does not have permission to perform the requested action.

**Common causes:**

- The API key was generated by a user whose role does not include the relevant module or action.
- The endpoint you are calling requires a higher permission level (e.g., Delete or Approve) than the key's associated user holds.
- The resource you are trying to access belongs to a different organisation or scope.

**Resolution steps:**

1. Review the permission level of the user who owns the API key under **Configuration → Users**.
2. If the user's permissions are insufficient, either update their module permissions or generate a new API key under a user account with the appropriate access level.
3. Confirm you are calling the correct endpoint and that the resource ID in your request belongs to your organisation.

<Note>
  For security reasons, Exsited does not expose which specific permission is missing in a 403 response. If you are unsure what permission is required for a given endpoint, refer to the API reference documentation or contact [support@exsited.com](mailto:support@exsited.com).
</Note>
