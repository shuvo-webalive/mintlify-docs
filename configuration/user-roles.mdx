Exsited uses a role-based access control model to keep your data secure and your workflows clean. Every user in your organisation is assigned a role that determines which modules they can access and what actions they can perform. Understanding these roles — and applying the principle of least privilege — helps you reduce risk and maintain a tidy audit trail.

## The Four Roles

| Role | Description |
|---|---|
| **Admin** | Full access to all modules, configuration settings, user management, billing, and audit logs. Assign this role sparingly. |
| **Manager** | Can create, edit, and approve records across assigned modules. Cannot access system-level configuration or manage users. |
| **Staff** | Can create and edit records within assigned modules. Cannot approve records or access configuration settings. |
| **Viewer** | Read-only access to assigned modules. Cannot create, edit, or delete any records. |

## Inviting a New User

<Steps>
  <Step title="Open User Management">
    Navigate to **Configuration → Users → Invite User**.
  </Step>
  <Step title="Enter user details">
    Provide the user's full name and work email address.
  </Step>
  <Step title="Select a role">
    Choose the appropriate role from the dropdown: Admin, Manager, Staff, or Viewer.
  </Step>
  <Step title="Set module access">
    Toggle on the specific modules this user should access. A Manager role does not automatically grant access to all modules — you must enable each one individually.
  </Step>
  <Step title="Send the invitation">
    Click **Send Invite**. The user will receive an email prompting them to set a password and complete their profile.
  </Step>
</Steps>

## Changing a User's Role

<Steps>
  <Step title="Locate the user">
    Go to **Configuration → Users** and find the user in the list.
  </Step>
  <Step title="Open user settings">
    Click the user's name to open their profile.
  </Step>
  <Step title="Update the role">
    Select the new role from the **Role** dropdown and click **Save Changes**.
  </Step>
</Steps>

<Warning>
  Changing a user's role takes effect immediately. If you downgrade a user from Admin to Staff while they are logged in, their session permissions will update on their next page load.
</Warning>

## Module-Level Permissions

Beyond the top-level role, you can fine-tune what each user can do within a specific module. For example, a Staff user might be able to **view** orders but not **create** them, or a Manager might have full access to Inventory but only read access to Finance reports.

The following permission levels are available per module:

| Permission | What it allows |
|---|---|
| **None** | Module is hidden entirely from the user. |
| **View** | User can open and read records but cannot make changes. |
| **Create** | User can create new records. Includes View. |
| **Edit** | User can modify existing records. Includes View and Create. |
| **Delete** | User can remove records. Includes all permissions above. |
| **Approve** | User can approve or reject records in a workflow. Includes View. |

To edit module permissions, go to **Configuration → Users**, open the user's profile, and adjust the toggles under **Module Access**.

## Best Practices for Least-Privilege Access

<Tip>
  Grant users only the access they need to perform their job — nothing more. This limits the blast radius of accidental changes and keeps your audit logs meaningful.
</Tip>

- Start every new user with the **Viewer** role and expand permissions as needed.
- Review user permissions quarterly, especially after staff changes.
- Avoid assigning the **Admin** role to more than two or three people in your organisation.
- Use **Manager** roles for team leads who need approval authority but do not need system configuration access.
- Remove or deactivate users promptly when they leave the organisation.

## Deactivating a User

To deactivate a user, open their profile under **Configuration → Users** and click **Deactivate Account**. Deactivated users cannot log in, but their historical records and audit trail entries are preserved.

<Warning>
  Deactivating a user does not delete their data. If you need to permanently remove a user's records, contact your Exsited account manager.
</Warning>
